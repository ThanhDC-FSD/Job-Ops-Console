# 10.1 Giải thích hệ thống hiện tại

## Mục đích tài liệu

Tài liệu này mô tả trạng thái hiện tại của hệ thống theo hai lớp:

- `Góc nhìn UI / showcase`: toàn bộ các page hiện có để phục vụ làm mới video showcase.
- `Góc nhìn vận hành / kỹ thuật`: các workflow, ràng buộc runtime, scheduler, logging, và các điểm cần lưu ý khi phân tích tối ưu.

Tài liệu này không thay đổi nghiệp vụ. Mục tiêu là đồng bộ nhận thức để có thể:

1. lên kịch bản video showcase mới theo đúng UI đang có
2. hiểu mối liên hệ giữa từng page và backend
3. xác định đúng điểm nghẽn trước khi tối ưu tiếp

## Tóm tắt hệ thống

Hệ thống hiện tại là một `Job Ops Console` chạy cục bộ, tập trung vào chuỗi nghiệp vụ:

1. thu thập dữ liệu việc làm
2. chuẩn hóa và lưu trữ dữ liệu
3. hỗ trợ đánh giá độ phù hợp giữa CV và JD
4. hỗ trợ tạo CV / cover letter / artifact liên quan
5. theo dõi jobs, trạng thái ứng tuyển, analytics, learning, và automation trong cùng một console

Các thành phần chính:

- frontend React: giao diện điều hành
- backend FastAPI: API điều phối jobs, learning, schedules, runs
- APScheduler: chạy lịch định kỳ và lịch một lần
- SQLite: lưu jobs, learning data, automation runs, schedule metadata, completion profiles
- các script Python nội bộ: crawl, ETL, prediction, CV generation
- local model / local gateway: phục vụ một số workflow suy luận hoặc enrichment

Frontend structure note:

- `apps/frontend/src/App.jsx` is now a thin application shell for bootstrap, tab state, and top-level dispatch only.
- Page entry modules now live under `apps/frontend/src/pages/` so future page changes can stay localized without editing the root app shell.
- Runtime behavior, API calls, and tab routing stay backward-compatible with the previous single-file UI.

## 2. Jobs

### Vai trò

`Jobs` là workspace thao tác chính với danh sách job còn khả năng xử lý tiếp.

Đây là nơi operator:

- lọc jobs theo nhiều điều kiện
- mở chi tiết job
- đánh dấu thủ công
- sinh CV
- chạy apply flow hoặc thao tác liên quan
- xóa các job không còn cần thiết

### Nghiệp vụ chính

- danh sách job có filter / sort / paging
- phân biệt trạng thái theo stage
- thao tác trên từng job:
  - `Generate CV`
  - `Apply`
  - `Mark Applied Manual`
  - `Delete`
- mở modal chi tiết job

### Logic vận hành đáng chú ý

- tab `Jobs` mặc định quay về stage `filtered` khi mở như hành vi release
- backend stage `filtered` chỉ trả các job còn khả năng xử lý tiếp
- các job đã suy ra là `company_under_review`, `manual_only`, `closed_no_longer_accepting` bị loại khỏi danh sách filtered
- nếu job đã có CV sẵn thì UI hiện `CV` + `Apply` + `Mark Applied Manual`
- nếu job chưa có CV thì mới hiện `Generate CV`
- Jobs filter labels, multi-select summaries, and toolbar buttons now keep safe fallback text so a missing locale key cannot blank the page chrome.
- Jobs filter dropdowns now close on outside click and use tighter min-width rules so multi-select panels do not overlap neighboring filter fields.
- Jobs now shows an explicit no-results diagnostic with the active filter summary plus a `Clear extra filters, keep search` action, so persisted browser filters no longer make company searches like `WorldQuant` look like crawl failures.
- Jobs detail modal also uses safe fallback labels for company, location, language, posted date, and rule controls so the JD view cannot degrade into `undefined:` rows when a translation key is missing.
- Jobs country and region filtering now falls back to lightweight `location` normalization when `job_location_enrichment` rows are missing, so broad geography filters no longer collapse to only the tiny subset of jobs that already had persisted country enrichment.
- Jobs detail now also shows the crawl-time LinkedIn applicant snapshot from `applicant_insight`, keeping the UI lightweight by rendering the captured count text directly instead of adding a new analytics flow.
- Generate CV now saves the artifact text bundle and immediately runs blocking materialization inside the same generate request, so a successful `Generate CV` response already contains TXT, DOCX, PDF, cover-letter, and fit-report paths without relying on a later preview repair pass.
- Generate CV responses and the frontend preview cache now trust the backend's actual `has_materialized_artifacts` and `preview_state` fields instead of forcing `materialized`, so failed renders fall back cleanly to artifact-text preview without showing fake paths.
- Generate CV prompt now requests `experience_summary` and `cover_letter` from the LLM (still grounded only in MASTER_CV evidence) so the generated CV/portfolio/cover-letter texts stay stylistically consistent across all artifacts before DOCX/PDF materialization.
- CV preview now opens with a loading shell when metadata or file text is still being assembled, and the modal repeats `Loading...` placeholders so users can distinguish a slow load from an error.
- CV preview now yields one browser paint before the preview fetch starts and ignores stale preview responses, so fast gateway hits no longer skip the visible loading shell and rapid reopens cannot overwrite the active modal with older data.
- CV preview repair requests no longer render TXT, DOCX, and PDF inline on the user-facing `cv-preview` request path; the API now queues materialization in a background worker, returns artifact text immediately, and the modal polls lightweight preview reads until real paths appear.
- CV preview UI now derives the displayed state from actual visible artifact paths plus artifact text, so a stale or inconsistent payload cannot label the modal as `Materialized artifacts` while every path row is still empty.
- Shared modal chrome now falls back to `Close` when the locale key is missing, so modal action buttons do not render as empty controls.
- Jobs detail now falls back to payload crawl fields such as `workplace_type`, `work_model`, and `job_insights` when `normalized_work_model` is empty, so remote or hybrid labels survive partial ETL rows.
- Jobs detail and work-model normalization now avoid using soft fit-result wording like `flexible or remote-friendly setup` as proof of a remote role; they instead prefer stronger payload evidence such as explicit work-model lines, `Primary Location` street-address headers, and `working together in person` copy before inferring `on_site`.
- Employment type inference now gives `contract` higher precedence than incidental `full-time` conversion copy, so LinkedIn rows that mention both no longer default to the wrong value.
- Maintenance backfill also scans the same payload workplace and insight fields, so older rows can recover `work_model` and `employment_type` without a heavy recrawl.
- LinkedIn `Apply` now supports `rehearsal_mode`, which opens Easy Apply, uploads the generated CV when needed, captures company-specific questionnaire state, and then stops before any final submit click.
- A new `GET /api/linkedin/apply/questionnaire-context/{job_id}` read path now tails the synced apply logs and returns pending field descriptors, latest debug artifact paths, compact CV evidence, and a ready-to-use prompt template for LLM-assisted answer drafting.
- The Chrome apply logger now defaults to backend port `8102` and captures richer field descriptors such as labels, placeholders, nearby prompt text, and select options, so company-specific forms can be reviewed without rescanning the full HTML blob.
- Jobs list `Easy Apply` filtering no longer depends only on `normalized_easy_apply`; it now uses an effective flag that falls back to validated detail rows and lightweight payload text signals, so crawled jobs with missing backfill do not disappear from the Easy Apply queue.
- The Jobs UI now exposes explicit `Easy Apply`, `Easy Apply Selected`, and `Easy Apply Only` actions, and it avoids offering browser automation on rows that are not marked as Easy Apply.
- Easy Apply runs that open the apply flow but still end at `apply_not_submitted` are now classified into a manual-review skip path instead of a hard failed automation status when login walls are not detected and apply controls are present.
- Easy Apply runtime now also auto-flags those `apply_not_submitted` rows as `manual_review_required` in tracking metadata, reducing repeated retries on the same jobs in later scheduled runs.

## 4. Reposts Analytics

### Vai trò

`Reposts Analytics` là page phân tích, dùng để nhìn dữ liệu từ góc độ xu hướng và hành vi đăng tuyển.

### Nghiệp vụ chính

- chạy analytics
- xem kết quả tổng hợp theo company / nhóm dữ liệu
- từ analytics có thể mở ngược về `Jobs` với preset filter tương ứng

### Analytics runtime notes

- `Reposts Analytics` now has 3 subtabs:
  - `Reposts`: legacy repost/company table, unchanged
  - `Language Trends`: a 90-day programming-language hiring view
  - `Stack Trends`: a 90-day stack-group view for `Full Stack`, `Frontend (FE)`, `Backend (BE)`, `AI/ML`, and adjacent mixes
- `Language Trends` adds:
  - local top-language trend lines built from SQLite job observations
  - regional concentration cards per language
  - country drill-back into `Jobs` with preset programming-language and country filters
  - external market context cards sourced from lightweight curated web fetches
  - a separate `Qwen lens` that is precomputed by a nightly refresh job, stored in SQLite, and then read by the page without calling Qwen on every open; the lens still interprets the same snapshot across economic, social/cultural, policy/regulatory, geopolitical/conflict, industry-cycle, technology, and regional dimensions
  - crawl expansion hints when the current evidence is too thin and the explanation would benefit from additional data sources or backfill targets
- `Stack Trends` adds:
  - group-level trend lines built from the same recent job window
  - heuristics that classify a job into a primary stack group from title, payload, and programming-language hints
  - regional concentration cards per stack group
  - country drill-back into `Jobs` with preset search and country filters
  - stack context cards that reuse the same lightweight curated source cache for broader explanations
  - crawl recommendations for buckets that are still too thin to trust as stable trend signals
  - a separate `Qwen lens` that is precomputed nightly, stored in SQLite, and read on page load so the request path stays fast while still expanding the stack narrative beyond local counts into broader market, social, and policy dimensions
  - crawl expansion hints that suggest which missing evidence would make the stack thesis more defensible
- local language-trend analytics now materializes the 90-day working set into temp tables inside one SQLite connection, so the backend does not recompute the same join/CTE chain multiple times in one request
- measured local smoke time dropped to about `608ms` for `/api/analytics/language-hiring-trends?days=30&top_n=4`
- external market context stays off the hot path:
  - backend fetches a short curated list of official sources with `requests` + `BeautifulSoup`
  - no JS rendering is used
  - facts are cached in-memory with a `6h` TTL
  - first fetch is slower, but cached requests dropped to about `520ms` in local verification
  - when the cache is stale, the backend now returns the last cached source list immediately and refreshes it in the background instead of blocking the chart view on a fresh crawl
- `Stack Trends` follows the same temp-table and cached-source pattern, so the added group analysis stays local-first and only pays the external crawl cost when the cached source context expires
- the new `Qwen lens` is intentionally separate from the chart hot path and now also separate from the request path:
  - a nightly scheduler job precomputes the lens for the common `30/60/90/120` day windows at `top_n=6`
  - the model output is persisted to SQLite in `analytics_trend_ai_snapshots`
  - the API reads the stored snapshot first and only emits deterministic fallback notes when a requested snapshot has not been materialized yet
  - page open no longer calls Qwen directly, which keeps the analytics tab responsive even when the local model is slow or temporarily unavailable
- the model output is structured JSON, which keeps the UI concise while still exposing thesis, dimension notes, crawl expansions, limitations, and what would change the view
- nightly refresh keeps the stored snapshot aligned with the current trend window and source context, so the page can stay read-only most of the time and still surface a model-backed lens
- nightly trend snapshot refresh now consistently computes snapshot expiry timestamps in the scheduler path, so the 01:10 refresh run no longer fails with a datetime helper `NameError`
- current curated sources:
  - GitHub Octoverse 2025
  - Stack Overflow Developer Survey 2025 Technology
  - JetBrains Developer Ecosystem 2024
- the UI renders local trend cards first and fills in source-backed explanations after the local charts are already available
- `/api/jobs/applied-stats` remains timezone-safe in repository date cutoffs, so Applied Jobs summary calls continue to return data instead of failing on missing UTC helpers

### Addendum: Stack Trends

`Stack Trends` is the new companion view for `Language Trends`.
It groups jobs into stack families such as `Full Stack`, `Frontend (FE)`, `Backend (BE)`, `AI/ML`, `Data`, `DevOps/Cloud`, and `Mobile`.

This view is intentionally local-first:

- it classifies jobs from title, payload, and programming-language hints already present in the database
- it reuses the same 90-day SQLite window and cached source fetch pattern as `Language Trends`
- it surfaces `crawl_recommendations` for thin buckets so extra crawl/backfill is only needed where coverage is weak
- it can explain the trend using current external context when cached source facts exist, and stale cache entries now refresh in the background instead of forcing every refresh to wait on a live crawl
- it now also exposes a Qwen-generated analyst lens that is refreshed at night, stored in SQLite, and read back by the page without another Qwen call on every open
- that lens is where broader hypotheses live, including cultural, social, economic, policy, and geopolitical interpretations plus crawl suggestions for missing evidence

## 6. Automation

### Vai trò

`Automation` là trung tâm vận hành scheduler và run-time execution.

Ngoài các bảng run/schedule hiện có, hệ thống giờ còn lưu thêm `automation_completion_profiles` để gom số record và thời gian thực thi theo `action_type` + ngày, rồi dùng snapshot đó để tính ETA cho từng run ngay trên API.

### Cấu trúc UI hiện tại

Automation hiện giữ lại đầy đủ các khối:

1. `summary cards`
2. `Manual Actions`
3. `Run Crawl Monitor`
4. `Create Schedule`
5. `Schedules`
6. `Runs`

Ngoài crawl / ETL / prediction / repair, Automation hiện cũng quản lý garbage cleanup schedule cho backup và log runtime.

### Điểm vận hành quan trọng

- `Run Crawl Monitor` hiển thị latest step, thời điểm bắt đầu, và `log file`
- mở log của run đang chạy sẽ mở tab viewer riêng và poll `/api/files/text`
- `Schedules` shows shutdown state through the inline badge in `Name`, so the table does not need a separate `Shutdown when completed` column
- `Schedules` keeps the current 9-column layout aligned with fixed column widths plus horizontal overflow, so long names and the 3-button action group stay readable instead of collapsing into narrow cells
- `Schedules` now defaults to `Next run` ascending, so the nearest upcoming execution is shown first for faster operator scanning
- `Schedules` now also shows estimated duration and estimated end time for the next occurrence by reusing completion profiles from recent runs
- the create/edit schedule form previews the next run window and warns when the new occurrence is likely to overlap an already-enabled schedule window
- when `pipeline_type=automate_easy_apply`, the schedule editor exposes job-filter fields (country, work model, employment type, programming languages, posted-within-days, search/company, has-CV) and persists them into `crawl_config.job_filters` without losing them on pause/resume
- `Runs` hiển thị log file, trạng thái, phase, progress, ETA dự đoán, pause / resume / stop
- pending scheduled runs có thêm `Recall` và `Set Time`
- pause is the checkpoint-based control path for pause-aware scripts, while `Stop` is the hard cancel path for runs that need immediate termination
- LinkedIn apply scripts now honor `SQLITE_APPLY_TIMEOUT_SECONDS` + `SQLITE_BUSY_TIMEOUT_MS` so transient SQLite contention does not immediately fail the apply pipeline.
- `linkedin_offsite_apply.py` opens the job DB in autocommit mode, configures `busy_timeout`, and retries snapshot writes when SQLite is temporarily locked so long apply batches do not abort near the end.
- Offsite Qwen prompts include a bounded instruction excerpt (questionnaire rules + offsite UI action selection heuristics) to improve candidate `candidate_id` choice without expanding prompt size into raw HTML.
- A new maintenance action `apply_self_heal_harness` can scan recent failed LinkedIn apply runs (stored in the same job DB pointed to by `JOB_DB_PATH`) for SQLite lock signatures and best-effort rerun them with safer SQLite timeouts; each attempt is recorded under `artifacts/harness/` and guarded by `tmp_seek_automation/locks/apply_self_heal_harness.lock`. For safer targeting, the harness also supports `--include-run-ids` to rerun only specific run ids.
- Automation now includes a dedicated generated-artifact repair schedule path for recent jobs, seeded by default at `01:00`
- Automation now also seeds a dedicated `Nightly Garbage Cleanup` schedule at `01:30` to remove backup and log files older than `10` days
- garbage cleanup now also scans `%LOCALAPPDATA%\\Temp\\job_ops_*` entries, so orphaned runtime SQLite/temp folders no longer sit outside the maintenance scope
- `job_ops_merge_tmp` now supports an optional size-cap cleanup mode: when enabled, the cleanup run deletes old `job_ops_merge_*.sqlite*` files (older than a configurable minimum age) until the folder drops under the configured cap, while staying bounded by the existing delete budget and avoiding broad Temp deletion risk
- scheduler sync now reconciles stale `automation_runs` rows before re-registering jobs, marking long-dead `running` and overdue `pending` rows as failed so idle maintenance is not blocked forever by orphaned state
- action runs and idle DB sync now snapshot `job_ops_*` temp usage before and after work, then log the delta with `run_id`, action name, and child PID when the temp footprint changes
- completion profiles are incrementally updated from completed run logs, so the runs table can read ETA snapshots from SQLite instead of recomputing them on every page open
- frontend shell now reads the shared full `i18n` source from `AppRuntime`, so the Automation page keeps its labels after refactors instead of rendering empty headings/buttons
- `linkedin_easy_apply` is now also a supported generic automation action command, so operators can queue rehearsal or final apply runs through `/api/actions/trigger` when explicit uploadable CV paths are already materialized.
