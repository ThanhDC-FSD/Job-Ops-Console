# 10.1 Giải thích hệ thống hiện tại

## Mục đích tài liệu

Tài liệu này mô tả trạng thái hiện tại của hệ thống theo hai lớp:

- `Góc nhìn UI / showcase`: toàn bộ các page hiện có để phục vụ làm mới video showcase.
- `Góc nhìn vận hành / kỹ thuật`: các workflow, ràng buộc runtime, scheduler, logging, và các điểm cần lưu ý khi phân tích tối ưu.

Tài liệu này không thay đổi nghiệp vụ. Mục tiêu là đồng bộ nhận thức để có thể:

1. lên kịch bản video showcase mới theo đúng UI đang có
2. hiểu mối liên hệ giữa từng page và backend
3. xác định đúng điểm nghẽn trước khi tối ưu tiếp

## Tóm tắt hệ thống

Hệ thống hiện tại là một `Job Ops Console` chạy cục bộ, tập trung vào chuỗi nghiệp vụ:

1. thu thập dữ liệu việc làm
2. chuẩn hóa và lưu trữ dữ liệu
3. hỗ trợ đánh giá độ phù hợp giữa CV và JD
4. hỗ trợ tạo CV / cover letter / artifact liên quan
5. theo dõi jobs, trạng thái ứng tuyển, analytics, learning, và automation trong cùng một console

Các thành phần chính:

- frontend React: giao diện điều hành
- backend FastAPI: API điều phối jobs, learning, schedules, runs
- APScheduler: chạy lịch định kỳ và lịch một lần
- SQLite: lưu jobs, learning data, automation runs, schedule metadata
- các script Python nội bộ: crawl, ETL, prediction, CV generation
- local model / local gateway: phục vụ một số workflow suy luận hoặc enrichment

Frontend structure note:

- `apps/frontend/src/App.jsx` is now a thin application shell for bootstrap, tab state, and top-level dispatch only.
- Page entry modules now live under `apps/frontend/src/pages/` so future page changes can stay localized without editing the root app shell.
- Runtime behavior, API calls, and tab routing stay backward-compatible with the previous single-file UI.

## 2026-04-08 Implementation Note: Interview Q&A Module Layout

`predict_interview_qa` still keeps the same operator flow, scheduler entrypoint, and CLI command:

- `.venv\Scripts\python.exe scripts\python\predict_night.py <args...>`

Runs that exit cleanly but print `[PREDICT] skipped disabled_by_flag` are now classified as `skipped` in automation history instead of `success`.

The runtime is now split into smaller modules under `scripts/python/interview_qa/`:

- `contracts.py`: runtime data contracts for jobs, ranked questions, and evidence chunks
- `job_loader.py`: SQLite job loading and manual JD decoding
- `external_crawl.py`: lightweight external fetch from non-LinkedIn seed URLs with robots-aware HTML parsing
- `ranking.py`: lightweight question ranking and compact evidence retrieval
- `prompts.py`: generation and vet prompts
- `schema.py`: JSON parsing and output validation
- `llm.py`: local backend dispatch for `ollama`, `llama_cpp`, and `gateway_ollama_chat`
- `reporting.py`: job JSON output plus summary JSON and Markdown
- `storage.py`: JSONL logging, cache DB access, output directory helpers
- `runner.py`: orchestration while preserving the old CLI behavior

The hot path is still the same business workflow, but with lower duplication:

- question ranking stays lightweight before any LLM call
- prompts only include shortlisted questions and compact evidence chunks
- payload context and lightweight external pages are cached before they reach the LLM stage
- model output is validated before persistence, so bad `evidence_ids` do not leak into saved artifacts
- cache keys are hashed and reuse the shared tuning cache DB
- CV preview now exposes cover-letter TXT, DOCX, and PDF paths explicitly when those artifacts exist
- CV preview keeps artifact diagnostics but leaves repair work to explicit repair flows and automation schedules

This keeps backward compatibility for automation while making the feature easier to test and safer to extend.

## 2026-04-09 Implementation Note: Interview Q&A Timeout Resilience

`predict_interview_qa` now protects long CPU-only local inference runs from aborting the entire batch when one local model call stalls.

Current resilience behavior:

- LLM HTTP calls now use configurable timeout and retry settings through:
  - `TUNING_PREDICT_QA_TIMEOUT_SECONDS`
  - `TUNING_PREDICT_QA_MAX_RETRIES`
  - `TUNING_PREDICT_QA_RETRY_BACKOFF_SECONDS`
- generation and vet prompts now cap evidence volume through:
  - `TUNING_PREDICT_QA_PROMPT_MAX_EVIDENCE`
  - `TUNING_PREDICT_QA_PROMPT_EVIDENCE_CHARS`
- transient local backend failures such as timeout, connection reset, or upstream `5xx` now retry with backoff
- a failed `vet` pass no longer discards the generated Q&A; the pipeline keeps the generation output and records `vet_error`
- a failed job no longer aborts the entire batch; the runner records the failure, continues remaining jobs, and still writes `summary.json` and `summary.md`
- cached predictions are now written into each new output directory so summary files and per-job JSON stay consistent on reruns

Performance intent:

- preserve user-visible throughput by avoiding full-batch restarts after one slow Ollama response
- keep prompt size unchanged while improving stability
- reduce duplicate compute by retaining successful job outputs even when later jobs fail

Company-targeted crawl update:

- `Run Crawl Filtered` manual actions now support both `Crawl All` and `Crawl Company Jobs`
- the crawl configuration stays collapsed by default and is only shown after the operator clicks `Run Crawl Filtered`, so the extra controls do not look like shared inputs for other manual actions
- `Crawl Company Jobs` accepts one `Company Name`, resolves the LinkedIn company page, derives `f_C` company filters when available, and then reuses the same extract, validation, fit, and DB persistence pipeline as the standard crawl
- the crawl adds a lightweight `resolve_company` phase for observability before the normal extraction phase starts
- performance impact stays low because company mode adds only 1 guest-search lookup request plus 1 company-jobs page request before the normal crawl
- if LinkedIn does not expose company ids on the company jobs page, the crawler falls back to a strict company-name keyword filter instead of changing downstream storage behavior
- if LinkedIn blocks the company jobs page with guest `HTTP 999`, the run now degrades to the same strict company-name keyword filter instead of failing at `resolve_company`
## 2026-04-10 Implementation Note: Interview Q&A Confidence Package

The `predict_interview_qa` workflow now carries a richer output contract while keeping the existing operator flow intact.

Key additions:

- facet-aware company dossier generation
- interview risk map generation
- rule-based confidence breakdown
- explicit reliability state
- lightweight same-domain crawl expansion with safe caps
- backward-compatible persistence for the prediction table and detail modal

The UI still keeps the same three output tabs:

- `Q&A Pack`
- `Interview Brief`
- `Gap & Drill Plan`

The new result fields are additive only:

- `company_dossier`
- `interview_risk_map`
- `confidence_breakdown`
- `reliability_state`
- `supported_claim_rate`
- `contradiction_count`
- `fallback_used`
- `open_unknowns`

The Interview Q&A tab now renders the company dossier and risk map from the normalized prediction detail payload, and the detail modal remains backward-compatible with legacy rows that do not have the new fields yet.

The prediction table now also exposes `Recall/Edit`, which reloads the stored input snapshot when available so operators can rerun a previous prediction with small edits. This keeps the old submission context available for direct editing instead of requiring a fresh manual rebuild of the form.

Automation run logs are pre-created when a run is queued, and the log viewer can fall back to stored run detail when the file path no longer exists. That prevents stale log links from failing with a hard 404 while keeping the real file-based log path as the primary source.

The interview prediction crawl now treats `www` and non-`www` variants of the same company site as one canonical same-domain surface, which reduces the chance that a valid company website is effectively reduced to only the homepage when the site redirects.

The generation prompt also carries dossier summaries plus source page titles and URLs, so the model sees a stronger company surface when separate About, Services, or Customers pages were fetched.

Performance intent stays the same as the rest of the system:

- avoid heavy crawl by default
- keep prompt assembly compact
- reuse cached external pages and prediction payloads when available
- do not add extra LLM passes unless the existing vet pass is already enabled

## 2026-04-11 Implementation Note: Pending Run Misfire Grace

`SchedulerRuntime` now registers date-triggered pending runs and schedule overrides with a short misfire grace window.

Why this matters:

- a `pending` `predict_interview_qa` run can be scheduled a few seconds before the backend finishes syncing jobs
- before this change, APScheduler could drop that run as a misfire and leave the run stuck in `pending`
- the new grace window keeps the run alive long enough to execute after minor startup or sync delay, without changing the broader workflow

This is a narrow runtime fix, not a redesign of the scheduler flow.

## 2026-04-11 Implementation Note: Interview Q&A Timeout Tightening

The prediction runner now defaults to a much shorter LLM timeout for `predict_interview_qa` so an unresponsive local model does not hold the job open for too long.

Why this matters:

- the workflow already has heuristic fallback logic
- a long blocked model call adds latency without improving the result when the backend is unhealthy
- a shorter timeout lets the runner fail fast and continue through the existing retry/fallback path

This reduces worst-case waiting time and improves job completion behavior under local Ollama stalls.

## 2026-04-11 Implementation Note: Interview Q&A Timeout Fallback Completion

`predict_interview_qa` now completes the run with a heuristic fallback payload when the local model backend times out or fails and fallback mode is enabled.

Why this matters:

- the run no longer dies with `returncode=1` after waiting on a stalled Ollama request
- the fallback payload is grounded in JD, CV, and company signals, so the output still stays usable
- the runner skips the extra vet pass after a model timeout, which avoids adding a second blocking model call in the degraded path
- prompt text is now more compact, which reduces token pressure on the local model and keeps the hot path lighter
