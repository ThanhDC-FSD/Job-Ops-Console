## Interview Q&A Input Semantics

The `Interview Q&A` panel now needs to be read as two input groups, because not every field controls the same source of data.

### Custom JD enrichment inputs

- `Company name`: metadata for a manually pasted JD. This makes the output easier to read and is the safest place to add future company-based discovery heuristics.
- `Company website`: the primary external seed URL for a custom JD. The pipeline can use this URL to fetch lightweight external evidence before ranking and answer generation.
- `JD text`: the manual job description body. If the text itself already contains `http` or `https` links, those links are also collected as extra seed URLs.
- `JD file`: convenience input that fills `JD text`; it is not a separate crawl source by itself.

### Database job window inputs

- `Recent days`: how far back the runner looks in the local jobs database when loading jobs automatically.
- `Max jobs`: the upper bound on how many jobs are loaded from that database window.
- These two fields do not mean "crawl the internet for 14 days" or "crawl 5 websites". They only limit DB job selection before prediction starts.

### Effective runtime behavior

- If the operator pastes a custom JD and does not provide `Job IDs`, the run enters `custom JD only mode`.
- In `custom JD only mode`, `Recent days` and `Max jobs` are ignored so the runner does not accidentally add unrelated recent jobs from the database.
- If the operator also provides explicit `Job IDs`, the run combines those database jobs with the custom JD input.
- For DB-backed jobs, external seed URLs can still come from normalized job payload fields such as company or apply URLs.

## Interview Q&A Output Contract

The `predict_interview_qa` output should be defined at two levels: batch-level artifacts and per-job prediction payloads.

### Batch-level artifacts

- `summary.json`: batch summary with `job_count`, `custom_job_count`, `db_job_count`, `completed_jobs`, `failed_job_count`, `failed_jobs`, `backend`, `model`, and generated file names.
- `summary.md`: human-readable summary of the same run for quick review.
- `events.jsonl`: stage-by-stage runtime log, including prompt sizing, external fetch, cache hit state, and per-job failures.
- `job_<id>.json`: one structured prediction file per DB job or synthetic custom JD job.

### Per-job output fields

- `job_id`, `title`, `company`, `company_website`, `location`: normalized identity fields for the prediction target.
- `external_seed_urls`: the exact URLs used as crawl seeds for lightweight external enrichment.
- `source_documents`: the supplemental documents that actually entered the ranking and evidence path.
- `questions`: the ranked interview question candidates selected for this job.
- `evidence_chunks`: the traceable evidence set used to support answer generation and vetting.
- `qa`: the final interview Q&A list, where each item should include `question`, `answer`, `evidence_ids`, and `confidence`.
- `metrics`: latency and token-like backend counters for generation and optional vet pass.
- `generated_at`: UTC timestamp for the persisted result.

### Expected output by input pattern

| Input pattern | Expected output behavior |
|---|---|
| `Job IDs` only | One `job_<id>.json` per DB job. `company` and seed URLs come from DB payload normalization. |
| `Recent days` + `Max jobs` only | A bounded batch from DB jobs in that window. `summary.json` should show `db_job_count > 0` and `custom_job_count = 0`. |
| `JD text` only | One synthetic `job_<id>.json` with `company = Manual input`, empty `company_website` unless a URL is found in the JD body, and Q&A generated from JD plus CV. |
| `JD text` + `Company name` | Same synthetic job, but `company` should be the entered company name instead of `Manual input`. |
| `JD text` + `Company website` | Same synthetic job, with normalized `company_website`, that URL present in `external_seed_urls`, and external crawl attempted if enabled. |
| `JD text` + embedded URLs | Those URLs should also appear in `external_seed_urls`, even if `Company website` is blank. |
| `Job IDs` + custom JD together | Mixed batch. `summary.json` should show both `db_job_count > 0` and `custom_job_count > 0`, with one output file per item. |

### Required interpretation rules

- `Company name` changes output labeling, not crawl behavior by itself.
- `Company website` changes both output labeling and crawl provenance because it is a primary seed URL.
- `Recent days` and `Max jobs` only change which DB jobs enter the batch; they do not directly change the schema of each job result.
- If external crawl returns no useful pages, the output is still valid as long as `qa` is derived from JD, CV, and any payload context that exists.
- If the vet pass fails, the output should still preserve the generation result and mark the vet failure in `metrics`.

## Analysis For The Current Design

- The current design is now much easier to reason about because every important input has a visible downstream effect in the output contract.
- `Company website` is the highest-value new field because it adds both crawl provenance and better evidence quality without forcing a broader redesign.
- `Company name` is still useful even before domain discovery exists, because it removes the ambiguous `Manual input` label from outputs and summaries.
- The custom-JD-only rule reduces accidental noise in the batch output, which improves answer relevance and lowers prompt size when the operator only wants one JD analyzed.
- The remaining gap is that `Company name` alone still does not discover the company domain automatically, so the best external-enrichment path still depends on an explicit website or URLs present in the JD text.
