# Overview
This document maps the current system exactly as implemented, anchored to the ordinal docs order (01–10). It highlights how data moves, where embeddings are created, where heuristic logic remains, and where retrieval is not wired into inference.

# Ordinal-Based Workflow Breakdown
[01] **Workflow Matrix**  
- Summarizes active pipelines: seed import, crawl extractor, chunk/embedding store, hybrid explanation enrichment, CV rewrite, local LLM gateway.  
- Indicates RAG substrate exists (embeddings) but only enrichment uses it; other flows remain heuristic.

[02] **Crawl Knowledge Pipeline**  
- Backfill no longer copies answer→explanation; sets `needs_enrichment`.  
- `_collect_daily_crawl_candidates` fetches URLs; `_fetch_url_text` pulls HTML (caps length).  
- `_extract_qa_from_text` builds Q/A + evidence window and structured draft.  
- `_upsert_crawled_item` writes `learning_sources`, `learning_questions`, `learning_answers`, `learning_question_chunks` (embeddings stored).  
- Mandatory `_enrich_explanations`: SLM-first, validates info gain/overlap/length; strict retry then deterministic fallback; publishes only when gates pass.

[03] **Learning + Quiz Architecture**  
- Queue-backed `learning_etl` via `schedule_jobs` + `schedule_queue`; processed single-run to avoid overlap.  
- Chunking + hashed embeddings stored in `learning_question_chunks`.  
- APIs `/api/learning/*` serve topics, quiz payload, submit, history.  
- Frontend quiz tab uses cached distractors; no runtime LLM. Retrieval not used at query time—answers/explanations come directly from DB.

[04] **RAG Workflow (current doc view)**  
- Job crawl produces `job_text_embeddings`; vector tables exist.  
- Current inference paths (jobs/CV rewrite) do not call any retrieval endpoint; embeddings are stored only.  
- CV rewrite still selects context heuristically (length filters/compression), not semantic search.

[05] **RAG Workflow v1 (doc, aspirational)**  
- Describes planned retrieval + routing; not wired. Treat as future intent; kept for completeness.

[06] **Fit Evaluation / LLM ETL Tuning**  
- `evaluate_cv_fit.py` runs heuristic fit scoring.  
- Borderline cases go to `fit_evaluation_queue`; LLM rerank via local gateway; results persisted in `job_fit_scores`.  
- No semantic retrieval in fit scoring; uses stored features/overlap heuristics.

[07] **LLM Enhancements Solution**  
- Hardens prompts/validation; defines SLM→LLM→deterministic fallback chain.  
- Adds auto-shutdown after ETL; operational safeguards only—no architectural change.

[08] **Logging Standard**  
- Logs: `backend.log`, `backend.error.log`, `apps/backend/app/logs/etl_runs/*.log`, `automation_runs`, `llm_prompts` manifests.  
- Provides traceability for crawls, enrichment, CV rewrite, fit runs.

[09] **ETL & CV Rewrite Flow**  
- Scrapers (LinkedIn/Seek/Apify) → parse/normalize → `job_posts`, `crawl_runs`.  
- Feature extraction, chunking, embeddings → `job_text_embeddings`.  
- Heuristic fit gate → `job_fit_scores`; borderline rerank (LLM).  
- CV rewrite: prompt assembly with heuristic context selection (no retrieval); LLM rewrite; validator; render docx/pdf; store artifacts in `Raw_CV`/`documents`.

[10] **System Workflow (end-to-end)**  
- UI tabs (Dashboard/Jobs/Learning/Automation) call FastAPI controllers.  
- APScheduler + AutomationService trigger bat scripts: `run_linkedin_jobs_jd.bat`, `run_linkedin_jobs_applied_tracker.bat`, `run_learning_etl.py`, `render_cv_docx.bat`.  
- SQLite stores: `job_ops_schema.sqlite`, `linkedin_jobs_jd.sqlite`, `learning_*`.  
- Files: `documents/`, `input/Raw_CV/`.  
- Local LLM gateway mediates LLM calls for enrichment, fit rerank, CV rewrite.

# End-to-End Flow (Narrative)
UI/Automation requests hit FastAPI → AutomationService schedules/executes crawls and learning ETL → Scrapers parse jobs → chunks+embeddings stored → heuristic fit scoring (optional LLM rerank) → CV rewrite assembles heuristic context, calls local LLM, renders artifacts → Learning ETL seeds/crawls questions, chunks+embeds, runs enrichment via LLM, stores publishable explanations → APIs serve jobs/learning data from SQLite; documents served from filesystem. Retrieval indexes exist but are not queried during CV rewrite or job serving.

# Module-by-Module Explanation
- **Controllers**: `automation_controller`, `job_controller`, `learning_controller` route UI/API to services; no retrieval endpoints.  
- **Services**:  
  - `AutomationService`: queue handling, lock files, bat execution.  
  - `LearningService`: seed import, crawl, chunk/embed, enrichment orchestration.  
  - `ExplanationEnrichmentService`: SLM-first generation, validation, fallback.  
  - `JobService/CvRewriteService`: fetch job detail, assemble prompts heuristically, call LLM, validate, render.  
  - `FitService`: heuristic scoring, optional LLM rerank.  
- **Repositories**: `learning_repository`, `schedule_repository`, `job repositories`, `meta_repository`; SQLite persistence.  
- **Scripts**: `run_linkedin_jobs_jd.py`, `render_cv_docx.py`, `enrich_explanations.py`, fit evaluators.  
- **LLM Gateway**: `local_llm_controller` proxy to Ollama/Qwen; used by enrichment, fit rerank, CV rewrite.  
- **Storage**: SQLite DBs; embeddings tables `job_text_embeddings`, `learning_question_chunks`; artifact files under `documents/`, `input/Raw_CV/`.

# Data Flow and Persistence
- Jobs: crawl → parse → DB (`job_posts`, `job_detail_validations`) → chunk/embed → `job_text_embeddings` → heuristic fit → `job_fit_scores` → artifacts to `documents/`.  
- Learning: seed/crawl → `learning_sources/questions/answers` → chunk/embed → `learning_question_chunks` → enrichment publishes `explanation_*` → quiz APIs read from DB.  
- Logs: ETL and automation run logs under `apps/backend/app/logs/`.  
- No vector search at inference; embeddings remain unused for runtime context.

# Current Context Selection Logic
- **CV Rewrite**: heuristic/rule-based (length filters, keyword snippets); no semantic retrieval.  
- **Fit Scoring**: heuristic overlap; LLM rerank only for borderline, no retrieval.  
- **Learning QA at runtime**: none; explanations precomputed, quiz uses DB.  
- **Retrieval substrate**: embeddings stored (`job_text_embeddings`, `learning_question_chunks`) but not queried during inference.

# Bottlenecks and Tuning Points
- Crawling/parse CPU and I/O bound; large HTML fetch caps (300k chars).  
- Chunking + embedding generation repeated per crawl; potential duplicate work.  
- CV rewrite prompts can exceed limits; compression is heuristic not retrieval-driven.  
- Enrichment LLM calls blocked when gateway auth fails (observed 401); no retry to alt backend.  
- Fit rerank queue runs sequentially; borderline spikes increase latency.  
- Single-threaded learning queue avoids overlap but limits throughput.

# Current Gaps
- No retrieval loop for CV rewrite, fit scoring, or job serving despite stored embeddings.  
- No semantic search endpoint; vector tables idle at inference.  
- Context selection remains heuristic; risk of token bloat and low relevance.  
- Learning quiz runtime does not personalize via retrieval.  
- Observability captures logs but not vector recall metrics.

# Tuning Recommendations (Current-State Safe)
1. Cache chunk/embedding generation across crawls to reduce duplicate compute.  
2. Add prompt-length guardrails in CV rewrite to trim low-signal sections before LLM call.  
3. Harden gateway auth/env loading to prevent enrichment failures (ensure INTERNAL_LLM_SHARED_TOKEN).  
4. Add lightweight health check for SQLite WAL errors (recent disk I/O issues).  
5. Instrument latency per stage (crawl, chunk, embed, LLM) in existing logs for baseline.  
6. Cap batch size in enrichment to avoid long-running queue items on CPU-only machines.

# Pre-RAG Measurement Plan (baseline before any RAG change)
- Measure: crawl→embed throughput (docs/min), chunk size distribution, token counts in CV prompts, LLM latency per service (rewrite, enrichment, fit rerank), fit-score agreement between heuristic and LLM rerank, quiz API latency.  
- Capture: top-k relevance (heuristic vs manual), prompt lengths, artifact sizes, gateway success/error rates, SQLite I/O wait times.

# Conclusion
The current system runs crawl + embedding pipelines, heuristic context selection, and LLM calls via a local gateway. Embeddings are persisted but unused at inference, leaving clear insertion points for future retrieval while keeping existing business logic intact. This document and diagram mirror the present state for accurate analysis, debugging, and tuning.
